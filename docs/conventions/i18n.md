# Internationalization (i18n)

Rules for user-facing copy, locale files, formatting, and localized system email.

Load this when writing or changing user-facing copy, adding a locale string or language, formatting dates/numbers/currency, or changing system-written email. Product scope lives in [overview](../product/overview.md) (language and currency) and [emails](../product/emails.md) (email language).

## Non-negotiables

1. **The UI ships in English and Spanish.** Every first-party user-facing string resolves through i18next in both languages. Third-party/vendor-mandated labels are the only exception.
2. **No hardcoded first-party copy.** Titles, labels, placeholders, `aria-label`s, alt text, toasts, empty/loading states, validation messages, and error copy all use `t`.
3. **Both locales change together.** A copy change updates `en` and `es` in the same change. Never ship an English-only key or a placeholder translation.
4. **Never translate data.** Venue names, menu text, people's names, identifiers, codes, and other business- or person-authored content render as stored. Menu localisation is deferred; stage 1 keeps one authored language per menu field.
5. **Language follows the person, currency follows the Business.** UI language comes from the User's language preference (browser language seeds it until set). Currency, tax, and the Business timezone do not.
6. **Format for the active locale.** Dates, times, numbers, and currency use the active UI language, not a hardcoded locale. Times shown in a venue context use the Business timezone where the product specifies it.
7. **System email follows the recipient.** System-written email uses the recipient's language preference (English/Spanish), falling back to English. A manager's own words are sent as written and are never translated.

## Frontend

### Runtime and files

- `frontend/src/i18n/config.ts` is the single source for supported language codes, namespaces, the storage key, the `SupportedLanguage` type, and the supported-language guard. The singleton, the language-options hook, and the test helper all consume it.
- `frontend/src/i18n/i18n.ts` is the single i18next singleton. `main.tsx` imports it for its side effect **before** React renders; nothing else calls `init`.
- Locale files live at `frontend/src/i18n/locales/<language>/<namespace>.json` and are discovered with `import.meta.glob`. `frontend/src/i18n/localeResources.ts` turns those modules into i18next resources for production and tests. Do not import individual locale JSON files into feature code.
- Namespaces are fixed in `config.ts`: `common`, `nav`, `auth`, `marketing`, `business`, `customer`, `employee`, `mode`, `errors`. `common` is the default and holds cross-cutting chrome.
- The chosen language persists in `localStorage` under `restaurant_pos_i18n_lng`. On first load, a saved valid choice wins; otherwise the browser's base language is used; otherwise English. Language changes go through `changeAppLanguage`, which rejects unsupported codes.
- The singleton sets `document.documentElement.lang` on init and on every language change. An unsupported stored value falls back before the document is touched. The static `index.html` language and title are fallbacks only; the title is the brand proper noun, not a build placeholder.

### Choosing a namespace

| Namespace | Owns |
|-----------|------|
| `common` | Loading, live-connection, language-switcher, and other cross-cutting chrome |
| `nav` | Navigation, account menu, audience labels, brand |
| `auth` | Sign-in, sign-up, recovery, email-confirmation copy |
| `marketing` | Public customer and business marketing pages |
| `business` | Business workspace pages, settings, validation copy |
| `customer` | Customer workspace pages |
| `employee` | Staff workspace pages |
| `mode` | Customer/Business mode selection |
| `errors` | Access denied, not found, and error-boundary copy |

Use the namespace of the surface you are editing. Do not create a new namespace for a single screen; add it to the owning namespace.

### Authoring keys and copy

- Nest keys by screen or feature, then by role: `profileSettings.logo.uploadLabel`, `login.errors.required`. Keys are lower camel case and describe meaning, not the English wording.
- Interpolate with `{{name}}`; never build a sentence by concatenating translated fragments.
- Use i18next plural keys (`_one`, `_other`, …) instead of manual `count === 1` copy.
- `<Trans>` is only for trusted, static markup. Never pass untrusted person- or business-authored text into `<Trans>`; render it as an interpolation value.
- Keep copy values out of constants, enums, and shared packages. Shared packages carry identifiers and enums; the frontend owns the labels.
- Do not put user-facing messages in the backend just so the frontend can display them. Map API outcomes to frontend keys (see [Server copy](#server-copy)).

### Language selection

- `LanguageSwitcher` is the only language picker; it appears in the public navbar and the account menu.
- The switcher and any language-dependent formatting read the active language from i18next, not from a component state copy.
- A language change applies immediately without a reload and does not change the person's Business, currency, or session.

### Formatting

- `frontend/src/lib/formatting.ts` is the shared formatting module for dates, date-times, numbers, and currency. Its pure helpers take the active language explicitly; React surfaces use `useFormatting` from `frontend/src/hooks/useFormatting.ts`, which subscribes to i18next so a language change re-renders immediately. Machine-facing `YYYY-MM-DD` parsing/formatting lives in `frontend/src/lib/calendarDate.ts`.
- Derive the formatting locale from the active i18next language (`en` → `en`, `es` → `es`); do not default to a locale unrelated to the UI language.
- Use `Intl` or date-fns locale data for dates, times, numbers, and relative times. Do not hand-format month names, separators, or decimal marks.
- Currency amounts use the Business currency and the active UI language for formatting. The UI language never changes the currency code or the stored amount. When the Business currency is missing, fall back to plain number formatting; never invent a currency.
- Pass `getDateFnsLocale`/the hook's `dateFnsLocale` to date-fns-based widgets such as the calendar.
- Keep machine-facing values (`<input type="date">`, API payloads, export fields) in ISO/stable form; localize only the display.

## Server copy

### System email

- Template copy is keyed by language, not hardcoded to English. The send path selects the recipient's language preference with an English fallback.
- One-time-link, security, and account emails are system-written and therefore localized. Business-authored content in an email stays as written.
- Email language belongs to the emails subject; the personal preference is stored on the User (users subject).

### API problem details

- RFC 9457 problem details are machine-facing. Do not add new English user-facing copy to a problem body for the SPA to render.
- The SPA maps known problem types/statuses to keys in `errors` or the domain namespace. The raw `detail`/`errors[]` message is a diagnostic fallback, not the primary user copy in a non-English UI.
- Existing `{ message }` auth responses follow the same rule during migration: stable outcomes are mapped in the client; the server string is not treated as translated UI copy.

## Testing

- Render UI tests through `renderWithI18n` / `createTestI18n` from `frontend/src/test/i18nTestUtils.tsx`; do not import the app singleton into a test. Pass `"es"` to create an isolated Spanish instance.
- Assert user-visible text against the English locale copy. When copy changes, update the locale files and the assertions together.
- Keep `en` and `es` structurally identical. The i18n suite must fail when namespaces, keys, plural families, or interpolation placeholders drift.
- Cover at least one non-English render when a change affects pluralization, interpolation, or formatting.

## Adding a language

1. Confirm the product change first; the shipped UI language list is a product decision, not a local tweak. Update [overview](../product/overview.md) and any affected product subject if the list changes.
2. Add the code to `SUPPORTED_LANGUAGES` in `config.ts`, and add its flag/label mapping.
3. Add `locales/<code>/<namespace>.json` for every namespace with full key and interpolation parity.
4. Add the locale to date/number formatting and the `common.languages.<code>` label.
5. Add a render test in the new language and run the i18n parity checks.

## Current drift to remove

The rail exists, but the migration is not complete:

- Hardcoded English remains in `frontend/src/pages/business/BusinessDeliverySettingsPage.tsx`, `BusinessMetricsSettingsPage.tsx`, and `BusinessOpenHoursSettingsPage.tsx`.
- Language choice is persisted only in `localStorage`; the User's language preference is not yet read or written.
- `frontend/src/services/serviceErrors.ts` prefers a raw server `detail`/field message, which can surface English text in a Spanish UI.
- `backend/src/auth/emailTemplates.ts` defines only English copy and hardcodes the `.en` template at each send site; recipient-language selection is not wired.
- There is no lint/CI guard against new hardcoded first-party copy.
